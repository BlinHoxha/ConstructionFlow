ConstructionFlow AI

Relational Database Schema, Entity Relationships &
Implementation Blueprint

Version 1.0 | October 2026 | ASP.NET Core / EF Core / PostgreSQL

Scope: multi-tenant construction management for Kosovo, including projects, estimates, procurement, site reports,
document intelligence, budgets, AI jobs and auditability. This is a proposed logical schema, not an existing production
database.

1. Architecture and conventions

Recommended approach: modular monolith with PostgreSQL, EF Core migrations, object storage for files, and
background workers for document/AI processing. Keep transactional project data relational; store large files outside
the database. Use UUID primary keys, UTC timestamps, decimal monetary values, and soft deletion only where
justified.

Rule              Recommendation
Primary keys      id uuid PRIMARY KEY; generated server-side or application-side
Tenant isolation  tenant_id uuid NOT NULL on tenant-owned records; tenant-scoped authorization and composite constraints
Money             numeric(18,2) + currency_code char(3); no floating-point currency
Quantities        numeric(18,4) and explicit unit_code; normalize units where required
Concurrency       row_version bigint or xmin strategy; optimistic concurrency on mutable records
Audit             created_at, created_by, updated_at, updated_by; append-only audit_event for sensitive actions
Deletion          RESTRICT for financial history; archive projects, do not cascade-delete approved documents
Naming            snake_case database columns; PascalCase C# entities; plural table names optional but consistent

9. Cross-tenant foreign key safety

A simple FK on project_id is insufficient if tenant_id is independently supplied. Prefer UNIQUE(tenant_id,id) on
tenant-owned parent tables and composite FKs (tenant_id,project_id) -> projects(tenant_id,id), repeated for relevant
references. In EF Core, use composite alternate keys and enforce tenant scope in application services. Never trust
tenant_id from an arbitrary client request.

12. EF Core mapping example

Example of the tenant-safe relationship principle (illustrative C#):

modelBuilder.Entity<Project>().HasAlternateKey(x => new { x.TenantId, x.Id });
modelBuilder.Entity<DailyReport>().HasOne(x => x.Project)
.WithMany().HasForeignKey(x => new { x.TenantId, x.ProjectId })
.HasPrincipalKey(x => new { x.TenantId, x.Id });

Use value converters or strongly typed IDs if desired. Define monetary rounding and currency conversion explicitly.
Apply restrictive deletion behavior for financial and audit records.

15. Decisions to confirm before implementation

Confirm whether subcontractors require their own login, whether one company may own multiple legal entities, how
VAT and invoice numbering work in target customers, whether material stock must be tracked, whether budgets are
per project or per phase, and whether approvals need multi-stage signatures. These choices affect table boundaries
and constraints.

This schema is designed as an implementation blueprint. Before production, complete a full physical schema
migration review, data protection review, and performance test with realistic project/document volumes.
